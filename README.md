# Автозаказ товаров для УТ 11

Демонстрационное расширение для «1С:Управления торговлей» 11 (проверено на 11.5.11). Оно рассчитывает потребность в пополнении запасов по складам и магазинам: учитывает остатки, продажи, товары в пути и непроведенные заказы. По результату расчета создает черновики заказов поставщикам (закупка) и заказов на перемещение (пополнение магазина с распределительного центра).

**Стек:** 1С:Предприятие 8.3, «Управление торговлей» 11 (регистры ТоварыНаСкладах, ВыручкаИСебестоимостьПродаж, ЗаказыПоставщикам, ЗаказыНаПеремещение; документы ЗаказПоставщику, ЗаказНаПеремещение), расширение конфигурации (заимствованные объекты), запросы с временными таблицами и виртуальными таблицами регистров, регистр сведений, управляемая форма, регламентное задание, HTTP-сервис (стенд для тестов), Python (pytest), BSL Language Server, GitHub Actions.

## Что делает

Параметры пополнения задаются в регистре сведений «Параметры пополнения запасов» (раздел «Закупки») по складу и номенклатуре:

| Параметр | Смысл |
|---|---|
| Страховой запас, дней | Запас на время поставки и колебания спроса |
| Заказывать на дней | На сколько дней продаж рассчитан заказ сверх страхового запаса |
| Минимальный остаток | Остаток, ниже которого товар заказывается даже без продаж (например, для выкладки) |
| Кратность | Заказ округляется вверх до кратного (упаковка, коробка) |
| Минимальная партия | Меньше этого количества поставщик или склад не отгружает |
| Поставщик / Склад-источник | Как пополнять: заказом поставщику или перемещением со склада-источника |

Расчет по методу «минимум-максимум», для каждого склада, номенклатуры и характеристики:

```
средний расход   = продано за N дней / N
доступно         = свободный остаток (в наличии − к отгрузке) + в пути + в непроведенных заказах
точка заказа     = max(средний расход × страховой запас, минимальный остаток)
целевой запас    = max(средний расход × (страховой запас + заказывать на дней), минимальный остаток)
к заказу         = если доступно ≤ точки заказа: целевой запас − доступно,
                   не меньше минимальной партии, с округлением вверх до кратности
```

- **Продажи** берутся из регистра `ВыручкаИСебестоимостьПродаж` (по ключам аналитики номенклатуры) за N дней, заканчивая датой расчета.
- **В пути:** остатки `ЗаказыПоставщикам.КПоступлению` по складу и `ЗаказыНаПеремещение.КОформлению` по складу-получателю заказа.
- **Непроведенные заказы:** поставщикам и на перемещение, без пометки удаления, отмененные строки не учитываются. Поэтому повторный расчет (или регламентное задание) не создает дублей.
- **Перемещение со склада-источника** ограничено его свободным остатком. Остаток распределяется по магазинам по порядку, количество округляется вниз до кратности, в строке пишется пояснение.

## Как пользоваться

- **Обработка «Расчет заказов по запасам»** (раздел «Закупки»): дата расчета, за сколько дней брать продажи, склад (пусто — все склады с параметрами). Кнопка «Рассчитать» показывает таблицу с остатками, продажами, точкой заказа, целевым запасом и количеством к заказу (его можно поправить). Кнопка «Создать заказы» создает непроведенные заказы: поставщикам по паре «поставщик + склад» со статусом «На согласовании», на перемещение по паре «источник + получатель». Заказы проверяют и проводят вручную.
- **Регламентное задание «Автозаказ товаров»** (по умолчанию выключено) делает то же самое по всем складам с параметрами.

Программно:

```bsl
ПараметрыРасчета = ао_Автозаказ.НовыеПараметрыРасчета(); // ДатаРасчета, ДнейАнализа (30), Склады
Потребность = ао_Автозаказ.РассчитатьПотребность(ПараметрыРасчета);
Заказы = ао_Автозаказ.СоздатьЗаказы(Потребность);
```

## Как устроено

- `src/` — расширение `АвтозаказТоваров` (префикс `ао_`):
  - заимствованы справочники `Склады`, `Номенклатура`, `Партнеры`, `ХарактеристикиНоменклатуры`, роль `ПолныеПрава` (права на новые объекты) и подсистема `Закупки`;
  - свои объекты: регистр сведений `ао_ПараметрыПополнения`, общий модуль `ао_Автозаказ`, обработка `ао_РасчетЗаказов`, регламентное задание `ао_Автозаказ`, роль `ао_ИспользованиеАвтозаказа`.
- Расчет выполняется одним пакетом запросов. Параметры, ключи аналитики, заказы на перемещение и продажи сначала помещаются во временные таблицы: виртуальные таблицы не соединяются с другими таблицами напрямую, отборы задаются в их параметрах. Остатки, товары в пути, непроведенные заказы и продажи объединяются в одну таблицу и сворачиваются по складу, номенклатуре и характеристике.
- Заказы создаются в одной транзакции и заполняются стандартным `Заполнить()` документа УТ (организация, соглашение и прочее берутся по правилам конфигурации), затем записываются без проведения.

## Сборка и тесты

Нужны база «Управление торговлей» 11, платформа 8.3.17 или новее (собирается и проверяется на 8.5.1.1522, Linux), Python 3.11+.

```bash
# расширение и стенд в базе УТ (с проверкой модулей конфигуратором)
IB_USER="Администратор" scripts/build.sh <каталог файловой базы УТ>

# тесты: база опубликована на веб-сервере, HTTP-сервисы расширений включены
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
STAND_URL=http://127.0.0.1:8081/<публикация>/hs/auto-order-stand STAND_USER="Администратор" \
  PYTHON=.venv/bin/python scripts/test.sh -v
```

**Стенд** (`stand/`) — отдельное расширение `СтендАвтозаказа` с HTTP-сервисом. В рабочую базу его не ставят.

- `POST /scenario` создает склады, товары с характеристиками, поставщика, параметры пополнения и движения регистров: остатки, продажи, заказы в пути и непроведенные заказы. Все создается в режиме загрузки данных, к именам добавляется суффикс сценария, поэтому данные разных тестов не пересекаются.
- `POST /calculate` и `POST /orders` вызывают `ао_Автозаказ` и возвращают результат в JSON.

Тесты (`tests/test_auto_order.py`):

- дозаказ до целевого запаса; выше точки заказа — не заказывается; зарезервированное не считается доступным;
- кратность, минимальная партия и их сочетание;
- товары в пути (заказ поставщику и заказ на перемещение) и непроведенные заказы уменьшают потребность;
- границы периода анализа продаж;
- минимальный остаток без продаж; товар без продаж и минимального остатка не заказывается;
- характеристики считаются отдельно;
- перемещение ограничено свободным остатком склада-источника и распределяется по магазинам;
- создание заказов: заказ поставщику и заказ на перемещение не проведены, статус и строки верные; повторный запуск ничего не создает;
- неверный период анализа — ошибка.

CI (GitHub Actions): BSL Language Server по расширению и стенду, ruff. Проверка обращений к метаданным в запросах отключена: в репозитории только заимствованные объекты, а не вся конфигурация УТ.

## Ограничения

- Средний расход — простое среднее за период. Сезонность, тренд и дни без остатка (упущенные продажи) не учитываются.
- Товары, отгруженные перемещением, но еще не принятые (двухэтапное перемещение), в «в пути» не входят.
- Цены в заказ поставщику не подставляются: заказ создается черновиком для проверки менеджером.
- Параметры задаются по каждой паре «склад + номенклатура». Групповых настроек (по виду номенклатуры, по складу целиком) нет.
